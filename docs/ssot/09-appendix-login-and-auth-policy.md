## 부록 A. 로그인 화면 구조 (화면 묘사)

### A-1. 한 줄 컨셉

로그인화면은 화려한 랜딩이 아니라, **10초 안에 진입이 끝나는 인증 카드**이면서도, 로그인 후 들어갈 **동네 탐색 홈의 실루엣**이 은근히 느껴지는 화면이다.

### A-2. 레이아웃

```
[상단 미니 바]  지역선택 | 이용안내 | 고객센터

[메인 스테이지]
  흐린 배경: 공부방(지도형) + 과외(조건형) 홈 실루엣
  [중앙 로그인 카드]  로고 · 로그인 · 이메일/비번 · 소셜(네이버→카카오→구글)
  [카드 아래]  목적 칩 3개 · 짧은 안내 · 둘러보기
```

### A-3. 원칙

| 항목 | 잠금 |
|------|------|
| 역할 분기 | 로그인 화면에서 **강하게 요구하지 않음** — 공통 진입 카드 |
| 배경 | 홍보 사진 ✕ · **흐린 홈 실루엣** ○ (클릭 불가 · blur·저대비) |
| 소셜 | 보조가 아니라 **동등한 진입 경로** (한국 3축 순서) |
| 유료/권한 | 전면 설명 ✕ |
| 스크롤 | 긴 랜딩 ✕ · **한 화면 안에서 입력·진입** |

### A-4. 목적 칩 (카드 아래)

- 우리동네 공부방 찾기
- 과외쌤 비교하기
- 쪽지로 이어서 상담하기

### A-5. 문구 톤

| 구분 | 예시 |
|------|------|
| 제목 | 로그인 |
| 보조문구 | 우리 동네 공부방·과외쌤 찾기와 쪽지 연결을 이어서 이용하세요. |
| 회원가입 유도 | 처음이신가요? 회원가입 · 학부모·공부방·과외쌤 **공통 계정** |

## 부록 B. 인증정책 기본 원칙 (표준성·예측 가능성)

차별화보다 **예측 가능성**을 우선한다. 사용자가 새로 학습해야 하는 독특한 규칙보다, 국내 주요 서비스에서 기대하는 **표준 패턴**을 따른다.

| 항목 | 1차 잠금 |
|------|----------|
| 기본 로그인 | **이메일 + 비밀번호** |
| 소셜 | 보조가 아닌 **동등 진입** · 한국 **네이버 → 카카오 → 구글** |
| 계정 구조 | 역할별 별도 로그인 ✕ · **공통 계정 + 역할 확장** ○ |
| 이메일 | 로그인 ID · UNIQUE · trim + **소문자 정규화** |
| 동일 이메일 | 소셜·이메일 **연결 우선** · 자동 병합(다른 이메일) ✕ |
| 로그인 실패 | **이메일 또는 비밀번호를 확인해 주세요** (존재 여부 노출 ✕) |

## 부록 C. Cursor handoff — 1차 인증정책 구현 정리 (§16)

화면 창의성보다 **표준적이고 익숙하지만 단단한 동작 규칙**을 먼저 맞춘다.

### C-1. 회원가입 기본 원칙 (§16-1)

- 1차 회원가입은 **이메일 + 비밀번호 기반 공통 계정 생성**.
- **이메일과 휴대폰번호를 모두 필수**로 받는다. (공부방·과외쌤·학생 등록 항목이 아니라 최초 가입 항목)
- 이메일은 **로그인 ID · 연락처 메일 · 비밀번호 찾기 · 계정 확인** 기준값. **칸은 하나**.
- 휴대폰번호는 **계정 복구 보조 및 운영 안내** 기준값. 가입 단계에서는 **형식검사·정규화·저장만**. 본인확인(OTP) 없음. `phone_verified_at`은 가입에서 건드리지 않는다.
- 두 정보는 일반 회원 간 공개하지 않고 내부 보관한다. 검색·상세·쪽지·헤더 주표시값·표시명 fallback에 올리지 않는다.
- 외부 연락처 공개는 플랫폼이 먼저 하지 않으며, 필요하면 당사자가 쪽지 안에서 직접 교환한다.
- 회원가입 시 **SMS 패스코드/휴대폰 OTP 사용하지 않음**.
- 계정 생성 직후 **세션은 연다** (`users.status = active`). 그러나 **이메일 확인 전에는 가입 완료가 아니다**.

```
약관 동의
→ 공통 가입 폼 입력
→ 회원 구분 선택
→ 계정 생성 · 자동 로그인 (email_verified_at = NULL)
→ 확인 메일 발송
→ 이메일 확인 대기
→ 메일 링크 확인 (email_verified_at 기록)
→ 가입 완료
→ 역할별 기본등록 또는 홈 진입
```

### C-2. 이메일 확인 정책 (§16-2)

- **가입 완료의 정의:** `users.email_verified_at IS NOT NULL` **만**. `user_oauth_accounts` 존재·세션 존재·OAuth row는 통과가 아니다.
- 계정 생성·세션(`status=active`)은 확인 전에 허용한다. 미확인은 `pending`으로 막지 않고 **확인 대기 화면 + 서버 게이트**로 제어한다.
- 이메일 가입은 생성 직후 확인 메일을 보낸다. 확인 전에는 `#/signup/verify-email`에 머문다.
- **소셜 실메일:** 제공자가 준 실메일이고 생성 시 `email_verified_at`을 채운 경우만 확인 완료로 본다.
- **소셜 스텁**(`oauth_…@users.study114.local`)은 `email_verified_at = NULL`을 유지한다. 게이트·`me.php`도 미확인이다. 실메일 입력 후 확인 메일을 다시 보내고, 링크 클릭 후에만 완료다.
- 아래 행동은 **메일 확인 완료 후**에만 허용 (소셜 스텁 예외 없음). **저장뿐 아니라 보호된 조회/목록/메타**도 동일하다:
  - 기본등록 저장
  - 등록 상세 초안 작성·저장
  - 공개 등록/공개 전환
  - 쪽지 발송·답장 **및** inbox/스레드 목록/상세/개수/프리뷰/엔타이틀먼트 조회
  - 찜·비교·최근본·학생후기 목록
  - 유료 결제/유료 권한 활성화
  - 운영 콘솔(`/admin`, `AdminApi`)
- PHP `/auth/signup/basic` 직접 진입·`POST /api/auth/basic-register.php`·등록 API도 동일 기준이다.
- 확인 메일이 안 보이면 스팸함·프로모션함을 안내한다. 재전송 쿨다운은 10분.
- 확인 링크 재클릭: 이미 `email_verified_at`이 있으면 성공(`verified=1`)으로 본다. 그 외 만료·무효는 토큰 원문을 노출하지 않고 「이미 확인되었거나 만료된 링크입니다」만 보여 준다.

#### C-2-1. `admin_level` 예외 범위 (없음)

가입완료 게이트는 **관리자 role 전체 예외가 아니다.** 운영 테스트 계정 allowlist 예외도 **아니다.**

| 구분 | 실제 적용 |
|------|-----------|
| `users.admin_level` (`super_admin` / `sub_master`) | **콘솔 RBAC 전용.** 가입완료(`email_verified_at`)를 대체하지 않는다. |
| bootstrap 이메일 `jetty@naver.com` | 최고관리자 **등급 시드** 전용. 메일 확인 우회가 아니다. |
| `ops@dev.local` 등 레거시 시드 | 부마스터 **등급 fallback** 전용. 메일 확인 우회가 아니다. |
| 시장 SPA (`fetchSession` / chrome / `resolveAfterAuthUrl`) | `admin_level`이 있어도 미확인이면 확인 대기 화면으로 보낸다. |
| `AdminApi::requireAdmin` | 콘솔 API도 `email_verified_at` 필수. 미확인 관리자는 403 `email_verify_required`. |

한 줄: **관리자여도 `email_verified_at`이 없으면 가입완료 사용자가 아니다.**

#### C-2-2. optionalAuth 경로 분류

세션이 있어도 미확인이면 **게스트**로 취급한다. 공개 집계만 게스트에게 주고, 개인 메타는 확인 완료 세션에만 붙인다.

| 경로 | 분류 | 미확인 동작 |
|------|------|-------------|
| `GET /api/handoff/recommendations.php` `status` | 공개 읽기 | 게스트와 동일 집계 |
| 같은 GET의 `recommended` (개인 여부) | 보호 | 미확인이면 필드 생략 (게스트) |
| `POST /api/handoff/recommendations.php` | 보호 | `requireAuth` + verified |
| `GET/POST /api/handoff/favorites.php` | 보호 | verified 필수 |
| `GET/POST /api/handoff/compare.php` | 보호 | verified 필수 |
| `GET/POST /api/handoff/recent.php` | 보호 | verified 필수 |
| `GET/POST /api/handoff/student-reviews.php` | 보호 | verified 필수 |
| `GET /api/reviews/index.php?action=summary` 건수 | 공개 읽기 | 게스트 집계. 본문·`can_write`·`is_owner` 없음 |
| `GET /api/reviews/index.php?action=count` | 공개 읽기 | 게스트 집계 |
| `GET action=mypage` / `POST create` / `POST reply` | 보호 | verified 필수 |
| `GET /api/messages/threads.php` (목록·상세·`counts=1`) | 보호 | verified 필수 |
| `GET /api/messages/entitlements.php` | 보호 | verified 필수 |
| `GET /api/auth/me.php` | 세션 조회 | 미확인이어도 대기 화면용으로 허용. `email_verified=false` |

### C-3. 패스코드/OTP 정책 (§16-3)

- **회원가입용 패스코드 없음** · 휴대폰 문자 OTP 1차 제외 (비용·마찰·MVP).
- 인증이 필요할 때는 **이메일 링크 인증** 우선.
- 「비밀번호 설정 후 문자 인증번호」구조는 1차 기본안 **채택하지 않음**.

### C-4. 비밀번호 정책 (§16-4)

#### 기본 규약

| 규칙 | 값 |
|------|-----|
| 길이 | **8자 이상 14자 이하** |
| 조합 | **영문 + 숫자 + 특수문자** 필수 |
| 공백 | 허용하지 않음 |
| 확인 | 비밀번호 확인값과 **완전 일치** |

#### 금칙/차단

- 이메일 아이디(local-part) 그대로 포함 ✕
- 이름 그대로 포함 ✕
- 휴대폰 뒤 4자리 그대로 포함 ✕
- 널리 알려진 취약 패턴 차단 (예: `12345678`, `password1!`, `qwer1234!` 등)
- 동일 문자·숫자 과도 반복 ✕
- 키보드 순서·단순 증가 수열 등 쉬운 패턴 ✕

#### 구현 원칙

- **클라이언트 안내 + 서버 검증** 모두 필수 (프론트만 검사 ✕).
- 입력 필드 아래 규칙 짧게 명시:
  - 8~14자 · 영문, 숫자, 특수문자 포함 · 쉬운 비밀번호 사용 불가

### C-5. 비밀번호 찾기/재설정 (§16-5)

```
비밀번호 찾기 페이지
→ 가입 이메일 입력
→ 재설정 메일 발송
→ 메일 내 일회성 링크 (30분)
→ 새 비밀번호 입력
→ 재설정 완료 → 다시 로그인
```

| 원칙 | 내용 |
|------|------|
| 링크 | **일회성** · 사용 후 무효 · 만료 **30분** 권장 |
| 재설정 완료 | 이전 재설정 토큰 **전부 무효화** |
| 금지 | 임시비밀번호 발급 ✕ · 더미 인증번호(`123456`) ✕ · 외부 증명 없이 재설정 ✕ |

### C-6. 로그인 실패 문구 (§16-6)

- 계정 존재 여부 **직접 노출하지 않음**.
- 기본: **이메일 또는 비밀번호를 확인해 주세요**.

### C-7. 계정 연결/중복 (§16-7)

- 동일 이메일 → 이메일 가입·소셜 **같은 공통 계정으로 연결**.
- 서로 다른 이메일 → **자동 병합하지 않음**.
- 학부모/공부방/과외쌤 → **한 공통 계정 아래 역할 확장** 가능. **별도 계정으로 나누면 이메일도 서로 달라야 한다** (UNIQUE).
- 같은 이메일로 두 번째 공통 계정을 만들 수 없다.

### C-8. 미확인 계정 제한 (§16-8)

| 허용 | 제한 |
|------|------|
| 세션 유지 · 확인 대기 화면 · 확인 메일 재발송 | 가입 완료 · 기본등록 완료 처리 · 역할 홈을 가입 완료로 간주 · 공개 전환 · 쪽지 발송 · 유료 결제 |

→ **계정은 살아 있으나, 메일 확인 전에는 가입 완료가 아니다.** 공개/접촉/결제는 확인 후에도 기존 게이트를 유지한다.

### C-9. Cursor 구현 체크리스트 (§16-9)

1. 회원가입 직후 **자동 로그인** (`status=active`) · **가입 완료는 메일 확인 후**
2. 가입 단계 **SMS OTP 없음** · `phone_verified_at` 미변경
3. 이메일 확인 = **가입 완료 조건** + 공개·쪽지·결제 2차 게이트
4. 비밀번호 **8~14자 + 영문/숫자/특수 혼합**
5. 기본 취약 패턴 차단
6. **서버/클라이언트 동일 검증**
7. 비밀번호 찾기 = **이메일 링크 재설정**
8. 로그인 실패 문구 일반형
9. 동일 이메일 소셜/이메일 계정 연결 · **스텁은 메일 확인 전 미완료**
10. 역할 = 같은 메일로 새 계정 ✕ · **공통 계정 확장** ○ · 계정을 나누면 메일 다름

### C-10. 한 줄 최종 원칙 (§16-10)

**계정은 바로 만들되, 이메일 확인 전에는 가입 완료로 보지 않는다. 공개·접촉·결제는 확인 이후에도 한 번 더 막는다.**

## 부록 E. 비밀번호 찾기/재설정 화면 (§17)

이 절은 Cursor가 비밀번호 찾기 화면을 임의 해석하지 않도록, **페이지 구성부터 상태 흐름, 문구 톤, 예외 처리까지** 화면 언어로 풀어 쓴 구현 가이드다.

### E-1. 전체 원칙

- 비밀번호 찾기는 **계정 복구의 시작점**이지, 새로운 가입 유도나 서비스 소개 화면이 아니다.
- 화면은 로그인화면과 같은 톤을 유지하되, **더 조용하고 단순**해야 한다.
- 한 화면에는 **한 가지 목적만** 둔다.
- 단계는 아래 4단계로 고정한다.

```
비밀번호 찾기
→ 재설정 메일 발송 완료
→ 메일 링크 클릭 후 새 비밀번호 설정
→ 재설정 완료
```

- 회원가입 때처럼 휴대폰 문자 OTP, 별도 패스코드 입력, 추가 질문 단계는 넣지 않는다.
- 복구 과정에서는 제품 개성보다 **이해 속도, 안정감, 예측 가능성**을 우선한다.

### E-2. 비밀번호 찾기 시작 화면 (`#/find-password`)

| 요소 | 잠금 |
|------|------|
| 상단 | 로고(로그인으로) — 실루엣 **없음** |
| 제목 | 비밀번호 찾기 |
| 보조문구 | 가입한 이메일을 입력하면 비밀번호를 다시 설정할 수 있는 링크를 보내드립니다. |
| 필드 | 라벨 `이메일` · placeholder `가입한 이메일을 입력하세요` |
| CTA | 재설정 메일 보내기 |
| 하단 링크 | 로그인으로 돌아가기 · 회원가입 |

**입력 규칙:** 앞뒤 공백 제거 · 소문자 정규화 · 형식 오류 시 `올바른 이메일 형식이 아닙니다.`

### E-3. 동작 원칙 (계정 존재 비노출)

- 제출 후 **가입 여부와 관계없이 동일한 성공형 화면**으로 전환한다.
- API 응답 문구: `입력한 이메일로 비밀번호 재설정 안내를 보냈습니다. 잠시 후 메일함을 확인해 주세요.`
- 로그인 실패 문구 일반형 원칙(부록 C-6)과 일관된다.

### E-4. 재설정 메일 발송 완료 화면

| 요소 | 잠금 |
|------|------|
| 아이콘 | 체크(조용한 원형) |
| 제목 | 메일을 확인해 주세요 |
| 설명 | 재설정 링크 발송 · 스팸함 확인 · 재시도 안내 (2~3줄) |
| 버튼 | 메일 다시 보내기 · 이메일 다시 입력 |
| 하단 | 로그인으로 돌아가기 |
| 재전송 | **서버·클라이언트 동일 5분(300초)** · 버튼 비활성 + `메일 다시 보내기 (M:SS)` |
| API | `POST /api/auth/password/forgot.php` → `resend_available_in`(초) — 쿨다운 중에도 `ok:true` · 계정 존재 비노출 |

「가입되지 않은 이메일입니다」류 문구 **금지**.

### E-5. 재설정 메일 템플릿

| 항목 | 내용 |
|------|------|
| 제목 | `[우동공과] 비밀번호 재설정 안내` |
| 본문 | 요청 접수 → **HTML 버튼** `비밀번호 다시 설정하기` → **30분 유효** → 무시 안내 |
| 형식 | `multipart/alternative` — plain(링크 텍스트) + HTML(단일 CTA 버튼) |
| 구현 | `src/Auth/PasswordResetMailTemplate.php` |
| 금지 | 마케팅 문구 · 장황한 안내 · 배너 · 버튼 2개 이상 |

로컬 개발: `storage/logs/mail.log` — `--- plain ---` / `--- html ---` 구분 기록 (SMTP 대체). **Dev/QA만** plain 링크 복사로 검증.

### E-5a. validate-token API 해석 (고정)

| 필드 | 의미 |
|------|------|
| `ok: true` | API 호출·처리 자체는 정상 |
| `ok: false` | HTTP/핸들러 실패 (토큰 상태와 무관) |
| `status` | 비즈니스 토큰 상태: `valid` · `invalid` · `expired` · `used` |

⚠️ `ok: true, status: "invalid"` = “요청은 성공, 토큰은 무효”. 프론트는 `preview/auth-ui/src/password-reset-api.js` 계약을 따른다.

### E-6. 새 비밀번호 설정 (`#/reset-password?token=`)

| 요소 | 잠금 |
|------|------|
| 제목 | 새 비밀번호 설정 |
| 보조문구 | 새로 사용할 비밀번호를 입력해 주세요. |
| 필드 | 새 비밀번호 · 새 비밀번호 확인 |
| 규칙 안내 | 3줄 **기본 노출** (접기 ✕) |
| CTA | 비밀번호 변경하기 |

규칙 3줄: `8~14자` · `영문, 숫자, 특수문자 포함` · `쉬운 비밀번호 사용 불가`

진입 시 `GET /api/auth/password/validate-token.php`로 토큰 상태 선검증.

### E-7. 검증·오류 문구

| 상황 | 문구 |
|------|------|
| 길이 | 8~14자 이내로 입력해 주세요 |
| 조합 | 영문, 숫자, 특수문자를 모두 포함해 주세요 |
| 불일치 | 비밀번호가 서로 일치하지 않습니다 |
| 금칙/취약 | 사용할 수 없는 비밀번호입니다. 더 안전한 비밀번호로 다시 입력해 주세요 |

금칙어 상세(이메일·이름·휴대폰 등)는 **사용자에게 노출하지 않음**.

### E-8. 예외 상태 화면

| 상태 | 제목 | CTA |
|------|------|-----|
| 만료 | 링크가 만료되었습니다 | 재설정 메일 다시 받기 |
| 사용됨 | 이미 사용된 링크입니다 | 새 재설정 메일 받기 |
| 무효 | 유효하지 않은 요청입니다 | 비밀번호 찾기로 돌아가기 |

API `error`: `expired` · `used` · `invalid` — 기술 코드·스택 **노출 금지**.

### E-9. 재설정 완료

- 제목: `비밀번호가 변경되었습니다`
- 설명: `새 비밀번호로 다시 로그인해 주세요.`
- CTA: `로그인하기`
- **자동 로그인 금지** — 사용자가 새 비밀번호로 직접 로그인.
