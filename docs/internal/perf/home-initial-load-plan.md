### 1.3 오픈 후 롱텀으로 구현해야 할 방안 (몇 달)

#### 1.3.1 여러 앱 구조 정리
- **무엇**: 홈(home-ui)·찾기(search-ui, `/search/`)·공부방 상세등록(study-room-ui, `/register/room/`)·과외쌤 상세등록(tutor-ui, `/register/tutor/`)·인증(auth-ui)이 따로 된 앱이라, 메뉴를 누를 때마다 새 문서를 처음부터 연다. 하나의 셸(SPA)로 합치거나, 최소한 공통 코드·CSS를 같은 파일 이름으로 나눠 앱 사이에 캐시를 같이 쓰게 한다.
- **왜**: 찾기 앱 JS 542 KB + CSS 314 KB, 공부방 상세등록 JS 275 KB + CSS 161 KB(원본, 앞선 측정)를 메뉴 이동마다 따로 받는다. 같은 `home.css`·`tokens.css`·`design-system.css`가 앱마다 다른 이름으로 들어간다.
- **위험**: 라우팅·세션·지도 전부에 닿는 큰 공사. 단계별로.
- **수락**: 홈 → 찾기 → 상세등록 이동 때 새로 받는 KB, 메뉴 이동 시간.

#### 1.3.2 비로그인 홈 HTML 미리 그려 두기
- **무엇**: 빌드 때 게스트 홈의 첫 화면 글자(히어로 문구, 메뉴)를 HTML에 넣어 둔다. 지금 HTML은 `<div id="app"></div>`가 비어 있고 JS가 다 그린다.
- **왜**: JS를 받고 실행하기 전에도 글자가 보인다. 첫 글자 시간이 가장 크게 준다.
- **위험**: JS가 붙을 때 화면이 바뀌면 깜빡인다. 로그인 사용자는 이 HTML을 보면 안 된다(#225 역할 힌트와 맞춰야).
- **수락**: 시크릿 모바일 첫 글자 시간, 로그인 사용자 게스트 화면 노출 0.

#### 1.3.3 공개 데이터 서버 캐시
- **무엇**: 홈 공지·추천 목록·지역 목록처럼 자주 바뀌지 않는 공개 데이터를 서버에서 몇 분 단위 JSON 파일로 저장해 DB를 매번 부르지 않는다.
- **왜**: 공유 호스팅은 DB·CPU를 나눠 쓴다. 회원이 늘면 응답 시간이 흔들린다.
- **위험**: 관리자가 바꾼 내용이 몇 분 늦게 보인다. 개인화 데이터가 섞이면 안 된다.
- **수락**: 해당 API 응답 시간 전후, 관리자 변경 반영 시간.

#### 1.3.4 DB 인덱스 점검
- **무엇**: 데이터가 늘면 찾기 질의를 `EXPLAIN`으로 보고 실제 WHERE·ORDER BY에 맞는 인덱스를 단다.
- **왜**: 지금은 데이터가 적어 병목이 아니다. 늘어나면 풀 스캔이 생긴다.
- **위험**: 운영 SQL은 종현이 phpMyAdmin에서 실행. 쓰기 속도.
- **수락**: 주요 질의 `EXPLAIN` 결과·응답 시간.

#### 1.3.5 KT 경로와 호스팅 판단
- **무엇**: Cloudflare 접속 지점 문제. 2026-11-15 측정에서 LG망은 홍콩(HKG), KT망은 미국 LA(LAX)를 거쳤다. 무료 설정으로는 못 고친다.
- **판단 기준**: 위 최적화 뒤에도 국내에서 첫 문서 응답(TTFB)이 1.5초 넘게 계속되거나, 닷홈 자원 제한(트래픽·동시 접속 차단)이 생기면 상위 호스팅·국내 클라우드 이전을 비교한다. 기준은 디스크·트래픽이 아니라 CPU·메모리·동시 처리.
- **위험**: 이전은 DNS·SSL·OAuth·결제 허용 주소 전부를 바꾼다.
- **수락**: KT·LG 휴대폰에서 TTFB 전후.

#### 1.3.6 목표치와 실사용 측정
- **목표**: 모바일·PC 따로, 75번째 백분위 기준 LCP 2.5초 이하, INP 200 ms 이하, CLS 0.1 이하.
- **무엇**: 실제 방문자의 FCP·LCP·INP·CLS를 모으는 작은 측정(개인정보 없이 숫자만)을 붙이고, 주간으로 본다.
- **왜**: 지금 숫자는 박스·Cursor 로컬 측정뿐이다. 국내 실사용 값이 없다.
- **위험**: 측정 스크립트가 무거우면 안 된다. 개인정보 수집 금지.
- **수락**: 주간 리포트에 p75 세 값.
