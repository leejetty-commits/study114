## 3. 영역별 추가 점검 체크리스트

로그인 이후 기능은 테스트 계정이 없으므로 다음 항목을 운영자가 직접 확인할 수 있도록 정리합니다.

### A. 인증·세션·OAuth

- OAuth state가 로그인 요청마다 새로 생성되는가?
- state가 콜백에서 반드시 검증되는가?
- return_to가 사전에 허용된 경로만 받는가?
- OAuth 콜백에서 인증 코드 재사용이 차단되는가?
- 비밀번호 실패 횟수 제한이 서버에서 적용되는가?
- 로그인 성공 시 세션 ID가 재생성되는가?
- 로그아웃 시 서버 세션도 무효화되는가?
- 비밀번호 변경 후 기존 세션을 적절히 처리하는가?

### B. PHP API

- 모든 사용자별 조회에서 서버가 user_id 소유권을 검증하는가?
- 관리자 권한을 프론트엔드 값만으로 판단하지 않는가?
- 일반 사용자 요청에서 role 필드 변경을 차단하는가?
- JSON 입력 필드의 허용 목록이 정의돼 있는가?
- SQL 쿼리에 Prepared Statement를 사용하는가?
- Cron API가 인증 없이 실행되지 않는가?

### C. 프론트엔드

- 사용자 입력이 HTML로 직접 삽입되지 않는가?
- URL 파라미터가 위험한 DOM 삽입에 사용되지 않는가?
- postMessage 수신 시 origin을 확인하는가?
- 배포된 JS 번들에 운영 비밀값이 없는가?
- 소스맵에 민감한 내부 구현 정보가 노출되지 않는가?

### D. 인프라

- HTTPS 강제 적용
- HSTS 적용
- CSP 적용
- 디렉터리 리스팅 비활성화
- 백업 파일 웹 접근 차단
- `.git` 디렉터리 접근 차단
- PHP 오류 상세 내용의 외부 출력 차단

## 4. 우선순위별 조치 권고

현재 단계에서는 실제 취약점이 확인되지 않았으므로 아래는 위험도에 따른 예방적 조치 순위입니다.

1순위 — 홍보 전 필수 확인

높은 위험도

- OAuth state 및 return_to 검증
- 로그인 Rate Limit 서버 적용
- PHP API 사용자별 권한 검증
- Cron 및 스토리지 서명 인증

2순위 — 배포 전 권장

중간 위험도

- 쿠키 속성
- DOM XSS 방어
- 업로드 파일 검증
- JS 번들 및 소스맵 점검

3순위 — 운영 안정성 강화

낮은 위험도

- CSP 및 HSTS
- 구 호스트 접근 정책
- 오류 메시지 정보 노출
- 백업 파일 및 디렉터리 접근 차단

## 6. 점검의 한계와 다음 단계

이번 외부 점검에서는 메인 페이지의 접근 응답과 두 호환 호스트의 정본 도메인 리다이렉트만 관찰할 수 있었습니다. 실제 응답 헤더, 쿠키, 공개 API, JS 번들의 내용을 확보하지 못했으므로 위 항목을 통과 또는 취약으로 확정해서는 안 됩니다.

특히 이번 결과는 완료된 전체 보안 감사가 아니라 공개 접근으로 확인 가능한 제한 점검 결과입니다.

정밀도를 높이려면 다음 자료가 필요합니다.

- Vite 빌드 결과물의 공개 JS 파일
- 비밀값과 개인정보를 제거한 PHP API 소스
- API 엔드포인트 목록
- OAuth 콜백 및 return_to 처리 코드
- Cron·스토리지 인증 관련 코드

코드를 제공할 때는 실제 키, 비밀번호, 사용자 데이터가 포함되지 않도록 해주세요.

최종 의견: Study114는 유튜브 홍보를 시작하기 전에 인증·인가·API 보안의 실제 구현을 확인하는 것이 우선입니다. 현재 관찰 결과만으로 안전하다고 판정할 근거도, 취약하다고 판정할 근거도 충분하지 않습니다.
