# 70. 작업 루틴 정본 — 지시·작업·검수·보고·승인·배포

**상태:** 정본 (2026-10-07)
**적용 범위:** 이 저장소에서 일하는 모든 주체 — 그록봇, Cursor 메인 에이전트, Cursor 클라우드 에이전트, 로컬 에이전트, 하위 에이전트, 사람
**한 줄 원칙:** 사용자가 **특정 커밋**을 승인하기 전에는 `main`에 들어가지 않는다. 모든 단계는 저장소 안 작업기록에 남고 **push된 기록만 기록이다.**

---

## 1. 역할

역할은 사람·모델이 아니라 **자리**다. 누가 맡든 규칙은 같다.

| 역할 | 하는 일 | 할 수 없는 일 |
|---|---|---|
| **승인자** | 보고를 보고 승인·반려·보류. `main` 병합·배포 허가 | — (사용자만 맡는다) |
| **지시자** | 과제 정의, 지시서 작성, 작업자 배정, 재작업 지시 | 자기 지시를 스스로 승인 |
| **작업자** | 작업 브랜치에서 수정·자체점검·커밋·push | `main` push, 자기 작업 검수 |
| **검수자** | 2절 체크리스트로 검수, 통과/재작업 판정, 보고서 작성 | 작업자와 같은 세션·같은 에이전트가 맡는 것 |

**기본 배정 (사용자가 바꿀 수 있음)**

| 역할 | 기본 |
|---|---|
| 지시자 | 그록봇 또는 Cursor 메인 에이전트 (과제마다 작업기록에 명시) |
| 작업자 | Cursor 에이전트 (클라우드·로컬·하위 에이전트) |
| 검수자 | 지시자 쪽. 위험도 **높음**이면 작업자와 **다른 모델**의 독립 리뷰를 추가 |
| 승인자 | 사용자 |

## 2. 단계 (S0~S7)

| 단계 | 이름 | 완료 조건 | 작업기록 상태 |
|---|---|---|---|
| S0 | 과제 등록 | 작업기록 파일 생성, 지시서 **원문** 붙임, 위험도·허용 파일 명시 | `작업중` |
| S1 | 작업 | 작업 브랜치에 커밋·push. 커밋 메시지에 과제 ID | `작업중` |
| S2 | 자체점검 | 작업자가 3절 자동 검사 실행, 결과를 기록 | `검수대기` |
| S3 | 검수 | 검수자가 4절 체크리스트 판정. 하자 있으면 S1로 (회차 R1, R2…) | `검수중` / `재작업` |
| S4 | 보고 | 6절 형식으로 사용자에게 보고. **보고 대상 커밋 hash 고정** | `승인대기` |
| S5 | 승인 | 사용자 승인 문구를 **원문 그대로**, 시각과 함께 기록 | `승인` / `반려` / `보류` |
| S6 | 병합·배포 | 승인된 hash만 `main` 병합. Actions 결과(run ID) 기록 | `배포중` |
| S7 | 배포 후 확인 | 실제 사이트 확인 결과·스크린샷 경로 기록, 작업기록 닫기 | `완료` |

**재작업 규칙:** 검수 반려 사유는 항목별로 적고, 재작업 지시는 그 항목만 다룬다. 회차가 3회를 넘으면 지시서 자체를 다시 쓰고 사용자에게 알린다.

**승인 규칙**
- 승인은 사용자만 한다. 에이전트·그록봇의 "승인"은 효력이 없다.
- 승인은 **커밋 hash 단위**다. 승인 뒤 새 커밋이 생기면 그 커밋은 다시 S3부터.
- "배포해", "진행해" 같은 짧은 승인도 유효하다. 단, 어떤 보고(과제 ID·hash)에 대한 답인지 작업기록에 함께 적는다.

## 4. 검수 체크리스트 (S3)

검수자는 모든 항목에 `통과 / 해당없음 / 하자`를 적는다. `하자`가 하나라도 있으면 재작업.

1. **범위** — 바뀐 파일이 지시서 허용 목록 안인가. `git add -A`·amend(이미 push된 커밋)·`main` 직접 push 없음
2. **정본 대조** — 관련 `docs/ssot/*`, `docs/internal/*` 정본·레드라인(예: 54 ShopPage, 28 관리자)과 어긋나지 않는가. 정본을 바꿨다면 지시서에 근거가 있는가
3. **자동 검사** — 3절 결과가 실제로 통과인가 (작업자 보고를 믿지 말고 검수자가 재실행하거나 Actions 로그로 확인)
4. **동작 확인** — 위험도 보통 이상: 실제 화면을 역할별(게스트·학생·과외쌤·공부방·관리자 중 해당)로 열어 확인, 스크린샷 경로 기록
5. **운영 조치** — SQL(`sql/schema/*`), 환경변수(`VITE_*`), Secrets, `.htaccess` 변경이 있는가. 있으면 **배포 전에 사용자가 할 일**로 보고에 올린다
6. **독립 리뷰** — 위험도 높음: 작업자와 다른 모델이 diff를 처음부터 검토한 결과 첨부

## 5. 위험도

| 위험도 | 기준 | 추가 요구 |
|---|---|---|
| 낮음 | 문서·문구·스타일만 | 4절 1~3 |
| 보통 | 화면·프론트 로직·검증 스크립트 | + 4절 4 |
| 높음 | DB·SQL, 로그인·권한, 결제·유료, 비밀값·배포 설정, 여러 화면에 걸친 리팩터링 | + 4절 5·6, 운영 조치 완료 확인 후에만 배포 |

## 6. 보고 형식 (S4)

```text
[과제 ID — 제목] 승인 요청
- 결론: 배포 가능 / 조건부 가능 / 불가
- 대상: 브랜치 <name>, 커밋 <hash…>
- 바뀐 것: (사용자 관점 2~5줄)
- 검수: 범위 · 정본 · 자동검사 · 화면 · 운영조치 · 독립리뷰 (각 통과/해당없음)
- 배포 전 사용자 할 일: (SQL 적용 등. 없으면 "없음")
- 남은 위험: (없으면 "없음")
- 작업기록: docs/worklog/…
```

## 7. 작업기록

- 위치·양식: [`docs/worklog/README.md`](../worklog/README.md), 템플릿 [`docs/worklog/_TEMPLATE.md`](../worklog/_TEMPLATE.md)
- 작업기록은 **작업 브랜치에 코드와 함께 커밋·push**한다. 저장소 밖 폴더, 에이전트 가상 PC, 채팅에만 있는 기록은 기록으로 인정하지 않는다.
- 최소 커밋 시점: S0(지시서), S3(검수 판정), S5(승인), S7(완료).
- 여러 과제가 동시에 돌므로 **공용 목록 파일을 만들지 않는다** (충돌 방지). 찾을 때는 파일명·`git log --grep <과제ID>`를 쓴다.

---

## 8. 예외

- 운영 장애로 즉시 되돌려야 할 때도 **사용자에게 먼저 알리고** 지시를 받는다. 사후 보고로 대신하지 않는다.
- 이 문서와 다른 문서가 충돌하면 이 문서가 작업 절차의 정본이다. 기능 내용의 정본은 각 `docs/ssot`·`docs/internal` 문서다.
