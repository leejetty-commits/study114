## 판정

### 맞는 방향

- 기본필터에 두는 것, `has_request_summary` 네이밍, 공급자-only 카드 노출, 시드 문장 차단 방향은 004와 맞다.
- 마이페이지/등록으로 안 번졌다는 주장도 004 제외 범위와 맞다 (코드 diff는 remote에 없어 **주장만** 인정).

### 미완료 · 위험

1. **커밋/push 없음** → remote `main`의 `SearchService` 학생 SELECT에는 아직 `request_summary` / `special_request_note` / `has_request_summary`가 **없다**. 리뷰어가 코드를 잠글 수 없음.
2. **목록 SQL 미검증** → 로컬 PHP(`127.0.0.1:8080`) 꺼짐 + 브라우저 가로채기 재현. **필터가 진짜 DB에서 `request_summary` non-empty만 남기는지 미증명.**
3. **필터 판정 잠금 (사용자 추가 확정 2026-09-23)**  
   **한 줄 요청문을 작성한 학생만** 필터링되어야 한다.  
   - 판정 원본 = `students.request_summary` (trim 후 비어 있지 않음)  
   - `special_request_note`만 있는 학생은 **포함하면 안 됨**  
   - 시드/데모 문장·프론트 가짜 값은 **작성으로 치지 않음**  
   - visibility 플래그만으로 “있음” 판정 금지 (값이 비어 있으면 제외)
4. **역할 노출** — 학부모(parent) 응답에 본문을 넣는지 보고에 불명확. 기존 정책은 요청문 블라인드 유지 이력 있음. 보완지시문에서 공급자+관리자만 본문, 그 외 빈 문자열로 잠금.
5. **POST body 키 위치** — 검색 API는 `filters` 객체 안 키다. 보고의 `has_request_summary=1`은 **query string이 아니라** `filters.has_request_summary`여야 한다. (기존 `f_` → filters 수집 패턴)
