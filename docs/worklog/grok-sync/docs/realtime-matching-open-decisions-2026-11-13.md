## 종현이 정할 것 요약

1. **공부방 수업형태** — 새 목록을 만들지 말고, 등록에 이미 있는 수업운영방식 3개(그룹별 타임수업 / 타임별 무학년 수업 / 개인별 내방수업)를 그대로 쓴다. 학생 쪽에 같은 칸이 생기기 전에는 이 선택 조건을 적용하지 않는다. (공부방 확장 때)
2. **공부방 예산** — 새 구간표를 만들지 말고, 이미 있는 숫자(천원)가 같은 200천원 구간이거나 바로 옆 구간이면 일치로 본다.
3. **푸시 기술** — 1차는 쪽지만 보낸다. 푸시 ON/OFF는 숨기거나 「추후 제공」으로 두고, 웹푸시·앱·알림톡은 오픈 이후로 미룬다.
4. **최소 일치 규칙** — 지역 전제 + 필수 조건은 모두 맞아야 한다. 공급자가 켠 선택 조건도 모두 맞아야 하고, 켜지 않은 선택 조건은 보지 않는다. 점수·가중치는 쓰지 않는다.
5. **빈도 상한** — 조건이 맞는 프라임 공급자에게는 모두 알리되, 같은 학생은 한 쌤(원장)에게 한 번만. 쌤당 하루 20건, 학생당 「프라임카드 보내기」는 하루 5건.
6. **미성년 보호자 동의** — 1차에 별도 보호자 동의 화면은 만들지 않는다. 가입 말미 추천 동의(기본 끔)와 블라인드(이름 마스킹, 연락처 비공개)로 간다. (법률 자문이 아님)
7. **카드 수정·조건 변경 시 재매칭** — 베이직카드를 처음 등록할 때만 1회. 이후 수정이나 공급자 조건 변경으로는 다시 보내지 않는다.

## 1. 공부방 수업형태 항목값

- **출처:** 노션 정본 §6 미결, §5-4-B·§7-3 (초안 예시: 「소그룹 / 개별 진도 등」). 1차는 과외쌤이므로 공부방 확장 때 적용.
- **쟁점:** 공부방 필터의 「수업형태」를 어떤 값으로 받을지 정해 두지 않았다.
- **선택지**
  1. 새 목록(예: 소그룹 / 개별 진도 / 혼합)을 만든다.
  2. **(추천)** 공부방 등록에 이미 있는 수업운영방식 3개를 그대로 쓴다. 등록 화면 라벨은 「그룹별 타임수업」, 「타임별 무학년 수업」, 「개인별 내방수업」이다. (`preview/study-room-ui/src/state.js`의 `LESSON_OPERATION_TYPES`)
  3. 학생 기본정보의 수업형태(단독과외 / 그룹과외)와 억지로 맞춘다.
- **추천과 이유:** 2번. 이미 쓰는 값을 재사용하면 원장이 조건을 다시 배울 필요가 없고, 구현도 쉽다. 학생 기본정보의 「단독과외 / 그룹과외」는 과외쌤용이라 공부방 운영방식과 1:1로 맞지 않는다. 학생 쪽에 같은 3지선다가 생기기 전에는 이 선택 조건을 적용하지 말고(값이 없으면 통과), 공부방 확장 때 학생 칸을 맞추면 된다.
- **참고:** 화면마다 같은 값의 한글 라벨이 조금 다르다(예: 「타임별 무학년 수업」과 「타임별 혼합학년」). 매칭 필터 문구는 등록 화면 라벨을 따르는 것을 권한다. 라벨 통일 자체는 이 매칭 결정과 별개다.

## 2. 공부방 예산 구간

- **출처:** 노션 정본 §6 미결, §5-4-B(「공부방 수강료가 학생 예산과 겹칠 때」). 과외쌤 교습비도 「범위가 겹칠 때」로 이미 잠겨 있다.
- **쟁점:** 예산 일치의 구간을 새로 만들지, 이미 있는 숫자를 그대로 쓸지.
- **선택지**
  1. 20만 원 단위 등의 새 선택 목록을 만든다.
  2. **(추천)** 새 목록 없이, 이미 있는 숫자로 구간이 겹치면 일치로 본다. 학생 예산(`preferred_studyroom_fee_amount`, 천원)과 공부방 월 평균 수업료(`monthly_fee_manwon`, 천원)가 **같은 200천원 구간이거나 바로 옆 구간**이면 맞다고 본다. 200천원은 학생 카드 미리보기에 이미 쓰는 구간 폭이다(`budgetBandLabel`).
  3. 숫자가 정확히 같을 때만 일치로 본다.
- **추천과 이유:** 2번. 양쪽 모두 이미 천원 숫자를 받고 있다. 새 구간표를 만들면 입력 칸을 또 늘려야 한다.  Exact 일치는 너무 빡빡하고, 한 구간(또는 바로 옆)까지 허용하면 「겹치면 알려 드린다」는 카피와 맞다. 어느 한쪽 값이 비어 있으면 이 선택 조건은 적용하지 않는다.

## 3. 푸시 기술 (웹/앱)

- **출처:** 노션 정본 §6 미결, §3-11·§5-5(통지: 쪽지 기본 / 모바일 푸시 ON·OFF). 058 §5도 알림 채널을 미잠금으로 두었으나, 쪽지 기본은 이후 잠겼다.
- **쟁점:** 쪽지 외에 휴대폰 푸시를 1차에 넣을지, 넣는다면 어떤 기술로 할지.
- **선택지**
  1. **(추천)** 1차는 쪽지만 보낸다. 페이지의 푸시 ON/OFF는 숨기거나 「추후 제공」으로 두고, 웹푸시·앱 푸시·카카오 알림톡은 오픈 이후로 미룬다.
  2. 웹 브라우저 푸시(서비스워커)를 1차에 붙인다.
  3. 네이티브 앱 푸시(FCM 등)나 카카오 알림톡을 1차에 붙인다.
- **추천과 이유:** 1번. 지금은 웹 사이트이고 회원용 네이티브 앱이 없다. 웹푸시는 브라우저·아이폰 권한 이슈가 있고, 알림톡은 템플릿 검수와 비용이 따른다. 1인 운영으로 오픈이 급하면, 이미 잠근 쪽지함(채팅 알림·자주 쓰는 답변)만으로도 「오면 알려 드립니다」를 지킬 수 있다. 나중에 앱이나 푸시를 열 수 있게, 설계에 ON/OFF 자리만 남겨 두면 된다.
- **레퍼런스 (짧음):** 숨고는 요청이 오면 앱 푸시와 카카오 알림톡으로도 알린다. 앱이 있는 서비스의 방식이라, 앱이 없는 1차에는 그대로 가져오기 어렵다. ([숨고 고객센터: 요청서 알림](https://help.soomgo.com/hc/ko/articles/38804839497113))

## 4. 최소 일치 규칙

- **출처:** 노션 정본 §6 미결. 다만 §5-4 헬프(「선택 조건을 많이 걸수록 알림은 더 정확해지고, 횟수는 줄어들 수 있어요」)와 §3-7·§7-2(상시 매칭엔진·옛 가중치 방식 아님)가 방향을 이미 가리킨다.
- **쟁점:** 필수만 맞으면 보낼지, 켠 선택 조건까지 모두 맞아야 할지, 점수로 자를지.
- **선택지**
  1. **(추천)** 지역은 전제(반드시 일치). 필수 조건(과외쌤: 대상·과목 / 공부방: 학교급·과목)은 모두 일치. 공급자가 켠 선택 조건도 모두 일치(AND). 켜지 않은 선택 조건은 보지 않는다.
  2. 지역+필수만 맞으면 보내고, 선택 조건은 참고·정렬용으로만 쓴다.
  3. 가중치 점수가 임계값 이상이면 보낸다. (옛 단독 퀵매칭 방식)
- **추천과 이유:** 1번. 이미 써 둔 헬프 문구와 맞고, 점수 엔진을 만들 필요가 없다. 2번은 알림이 늘어 스팸처럼 느껴질 수 있고, 3번은 노션에서 보류한 옛 방식이다. 선택 값을 아직 안 채운 학생·공부방이 있으면 그 선택 축은 적용하지 않는다(필수처럼 막지 않음).

## 5. 빈도 상한 (쌤당 / 학생당)

- **출처:** 노션 정본 §6 미결. 058 §4는 상위 N·하루 상한·중복 억제를 권고만 했고 잠그지 않았다. 트리거 자체는 「학생 베이직카드 등록 시 1회」로 이미 잠김.
- **쟁점:** 한 학생 등록에 몇 명에게 알릴지, 한 쌤이 하루에 몇 건까지 받을지, 학생이 하루에 몇 통의 「내 프라임카드 보내기」를 받을지.
- **선택지**
  1. **(추천)** 조건이 맞는 프라임 공급자에게는 모두 알린다(상위 N 없음). 같은 학생→같은 공급자는 한 번만. 공급자당 알림은 하루 20건. 학생당 「내 프라임카드 보내기」는 하루 5건(추천 수신 동의한 학생만).
  2. 학생 1명당 상위 N명(예: 5명)에게만 알린다. 정렬 규칙이 필요하다.
  3. 오픈 초기에는 상한을 두지 않는다.
- **추천과 이유:** 1번. 지금 회원 수가 많지 않아 전원 통지가 부담이 작고, 「상위 N」을 정하려면 랭킹 엔진이 필요하다. 그래도 하루 상한과 중복 금지는 없어서는 안 된다. 학생이 한꺼번에 쪽지를 받지 않게, 수신 쪽은 더 낮게(5건) 두는 편이 안전하다. 숫자는 운영하다 조절하면 된다.
- **레퍼런스 (짧음):** 숨고는 거리별 순차(상위 N처럼 나눠 보내던 방식)를 폐지하고, 요청 즉시 고수에게 전달한다. ([숨고 고객센터: 요청서 전달](https://help.soomgo.com/hc/ko/articles/360039595651)) 김과외는 학생이 조건이 담긴 모집공고를 올리면 선생님이 수업 제안을 보내는 구조다. ([김과외](https://kimstudy.com/))

## 6. 미성년 학생 보호자 동의

- **출처:** 노션 정본 §6 미결, §3-14·§5-8(가입 말미 추천 수신 동의, 기본 끔). 관련 기존 잠금: 만 14세 미만은 1차 가입에서 제외(`docs/03-registration.md`, `docs/01-project-overview.md`). 학생 출생연도 칸은 2026-10-22에 제거했다(`284-cursor-directive-student-birth-year-remove.md`). 스키마 `prime_match_opt_in`은 기본 0이다(`sql/schema/084_student_prime_match_opt_in.sql`).
- **쟁점:** 추천 쪽지를 받는 동의 외에, 미성년 보호자 동의를 따로 받을지.
- **선택지**
  1. **(추천)** 1차에 별도 보호자 동의 화면은 만들지 않는다. 가입 말미 추천 동의(기본 끔) + 블라인드(성+마스킹, 전화·이메일 비공개)로 간다. 만 14세 미만 가입을 나중에 열 때 보호자 절차를 함께 설계한다.
  2. 미성년(또는 만 14세 미만)은 추천 수신 동의를 숨기거나, 보호자 확인 후에만 켠다.
  3. 미성년 학생은 추천 수신을 막고, 공급자에게 가는 알림만 허용한다.
- **추천과 이유:** 1번. 이미 만 14세 미만은 1차 가입에서 빠져 있고, 계정 주체를 학부모 기준으로 보는 잠금이 있으며, 출생연도를 걷어 내서 나이로 가릴 칸도 없다. 동의는 기본이 꺼져 있고, 매칭 쪽지는 연락처를 숨긴다. 1차에 동의 화면을 하나 더 만들면 가입만 복잡해진다. 이것은 **제품 운영 추천**이며 법률 판단이 아니다. 약관·개인정보 문구가 이 동의와 맞는지 오픈 전에 한 번 확인하는 것이 좋다.

## 7. 카드 수정·조건 변경 시 재매칭

- **출처:** 058 §5 「조건 변경 시 재매칭 여부·빈도」는 미잠금. 노션은 「학생 베이직카드 등록 시 1회 / 상시 매칭엔진 아님」만 잠그고, **수정**이나 **공급자 조건 변경**은 명시하지 않았다.
- **쟁점:** 학생이 기본정보를 고치거나, 쌤·원장이 희망조건을 바꾸면 다시 알릴지.
- **선택지**
  1. **(추천)** 베이직카드를 처음 완성·등록할 때만 1회. 이후 학생 수정, 공급자 조건 변경, 프라임 연장으로는 소급해서 다시 보내지 않는다. 같은 학생→같은 공급자 중복도 막는다.
  2. 학생이 기본정보를 바꿀 때마다 다시 매칭한다.
  3. 공급자가 조건을 바꾸면, 이미 등록된 학생을 다시 훑어 보낸다.
- **추천과 이유:** 1번. 노션의 「등록 시 1회」「상시 엔진 아님」과 맞고, 구현이 단순하며, 수정할 때마다 쪽지가 쌓이는 일을 막는다. 2·3번은 사실상 상시 엔진에 가깝다. 정말 필요해지면 오픈 뒤에 「다시 알림 받기」 같은 수동 버튼을 검토하면 된다.

## 이미 잠긴 것 (다시 정하지 않아도 됨)

노션 정본 §3·§7 기준. 058에서 열어 두었던 항목 중 아래로 잠긴 것은 이 브리핑에서 다시 논의하지 않는다.

- 단독 퀵매칭권 보류, 프라임 기간 선물만. 픽 제외
- 1차는 과외쌤, 공부방은 이후 확장
- 메뉴명 「프라임 실시간퀵매칭서비스」, 마이페이지 상시 노출, ON은 프라임 기간만
- 트리거: 학생 베이직카드 등록 시 1회. 지역 전제(과외쌤=시·군, 공부방=홍보지역)
- 과외쌤 필터 항목(필수: 대상·과목 / 선택: 성별·스카이·쪽집게·강의스타일·대학원 이상·교습비)
- 통지 기본은 쪽지, 매칭쪽지 무료, 블라인드, 추천 동의 기본 끔, 「프라임매칭」 태그
- 알림은 요약+미리보기+링크(카드 통째 삽입 없음). 「내 프라임카드 보내기」

프라임 카드 테두리 이펙트(노션 §③)는 매칭 미결이 아니라 별도 디자인 잠금이라 이 목록에서 제외했다.
