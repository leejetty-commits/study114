### 2-2. 「다음」 경유 시 유지되는仕組み

1. 상세 1단계 「다음」 핸들러 `preview/tutor-ui/src/screens/step-lesson.js:134-144`:

2. 입력칸→메모리 동기화 함수 자체는 `preview/tutor-ui/src/form-collect.js:41-63` (`syncLessonFromForm`: 성별·인원·연령대·산정방식·월 총 횟수·가격 설명·강의장소·추가 과목 행을 `FormData`에서 `state`로 복사).

### 2-3. 「이전」 시 사라지는 이유 (본건)

- 상세 1단계 「이전」 핸들러 `preview/tutor-ui/src/screens/step-lesson.js:126-128`은 **`syncLessonFromForm`을 부르지 않고** `navigate(basicComplete ? '/register/basic' : '/register/regions')`만 한다. 이동 자체는 `preview/tutor-ui/src/layout.js:25-27` (`navigate` = 해시 변경)뿐이다.
- 따라서 입력칸에만 있던 값은 `registerState`에 들어가지 못한 채 화면이 바뀌고, 기본정보 현황(`step-basic.js:276-278` 「상세정보로 이동」 → `navigate('/register/lesson')`)으로 다시 들어오면 `renderLesson`이 **옛 `registerState`(서버에서 불러온 값 또는 초기값)** 로 그려 선택이 비어 보이게 된다. 사라졌다는 안내 문구도 이 경로 어디에도 없다.
- **고칠 지점은 이 한 곳이다.** 「이전」 핸들러에서 화면을 바꾸기 **전에**, 「다음」 핸들러가 쓰는 것과 같은 `syncLessonFromForm(form, registerState)`으로 입력칸 값을 메모리에 옮겨 담는다. 이미 `step-lesson.js:10`에서 `syncLessonFromForm`을 import하고 있으므로 새 import도 필요 없다.

### 2-4. 방향의 경계 — 「이전」에서 서버 저장까지 하지 않는 이유

- 「다음」 경유 시와 동작을 맞춘다는 것은, **사용자가 나갔다 돌아왔을 때 입력이 남아 있는 것**까지다. 「이전」 핸들러에 `validateLessonState` 검사나 `saveAndNavigate` 서버 저장을 붙이면, 산정방식을 비운 값·형식이 안 맞는 값까지 서버 저장 판정을 새로 타게 되어 **저장 판정·필수 검사·서버 판정이 바뀌고 저장값·DB가 바뀐다**(6장 금지). 그래서 이번 수정은 **폼→메모리 동기화까지만** 「다음」과 같은 경로를 태우고, 검사·서버 저장은 붙이지 않는다.
- 이 경계 안에서 해결이 불가능하고 서버 저장(또는 경고 문구)까지 가야만 유지가 된다고 판단되면, 임의로 넓히지 말고 **중단 보고**하라(8장).

## 7. 확인 방법 (완료 보고에 전후로 적어라)

아래 세 케이스를 **수정 전(기준 동작)과 수정 후**로 나눠 보고하라. 화면으로 재현했는지, 코드 경로로 확인했는지를 구분해 적는다.

| # | 케이스 | 기대 결과 (수정 후) |
|---|---|---|
| A | 상세 1단계에서 값을 넣고 → 「이전」으로 나갔다가 → 기본정보 현황의 「상세정보로 이동」(또는 같은 진입 경로)으로 **다시 들어온다** | 넣었던 값(성별·인원·연령대·추가 과목·산정방식·월 총 횟수·가격 설명·강의장소)이 **그대로 남아 있다.** 다시 입력할 필요가 없다. (수정 전: 전부 비어 있음 — L-02 본건) |
| B | 상세 1단계에서 값을 넣고 → 「다음」으로 2단계까지 간 뒤 → 2단계 「이전」으로 1단계에 돌아온다 | 기존대로 값이 유지된다. 이 경로의 동작·검사·서버 저장은 전과 달라지지 않았다. |
| C | 상세 1단계에서 **아무것도 입력하지 않고** → 「이전」으로 나갔다가 → 다시 들어온다 | 기존과 동일하다. 없는 값이 새로 생기거나, 초기 표시(예: 연령대 등 기존 초기값 표시)가 달라지지 않는다. |

- **입력 보관 경로 보고 (필수):** 완료 보고에 「이번 수정으로 값이 남는 보관 경로는 무엇인지」를 적어라. 답은 코드 기준으로 **메모리(`registerState`)** 여야 하며, **새로고침(페이지 다시 불러오기) 시에도 유지되는지 여부**를 현재 구조 기준으로 함께 적어라. 새로고침 동작은 종현 확정에 없으므로 **임의로 요구·구현하지 말고, 현재 구조에서 되는/안 되는 그대로 보고만** 한다. (현재 구조: 첫 진입 때만 서버 저장값을 불러오므로, 서버에 저장되지 않은 값은 새로고침하면 마지막 서버 저장값으로 돌아가는 것이 정상 동작이다. 이를 고치려 하지 마라.)
- `git diff`에 허용 파일 밖 파일·문구·CSS가 없는지 확인한다.
- 재현 환경(로컬 dev 서버 등)으로 화면 확인이 어려우면, 그 사실과 코드 경로로 확인한 내용을 구분해 보고에 적는다. 확인하지 못한 것을 확인했다고 쓰지 마라.

## 8. 중단 보고 규칙 (t1844)

- **허용 파일(1개) 밖**을 고쳐야 하거나, 허용 파일이 **5개를 넘거나**, 동기화만으로는 유지가 안 돼 **서버 저장 방식·sessionStorage 신규 저장·경고 문구 방식**까지 가야 한다고 판단되면 **고치지 말고 멈추고 보고**하라. 보고에는 어느 파일·함수가 왜 필요한지, 허용 범위 안에서는 왜 안 되는지, 전후 동작을 적는다.
- 최신 `origin/main`의 「이전」·「다음」 핸들러가 2장의 전(before) 코드와 크게 다르면 억지로 맞추지 말고 멈추고 보고하라.
- 예상 diff(4장, 순증가 10줄)를 넘길 것 같으면 진행하지 말고 먼저 보고하라.
- 확정 방향(0장: 유지 쪽, 경고 아님) 밖의 방식이 필요해지면 임의로 만들지 말고 멈추고 보고하라.

3. **전후 대조**: 「이전」 핸들러의 전 코드→후 코드. 「다음」 핸들러·검사·서버 저장 경로를 건드리지 않았음을 적는다.

7. **멈춘 지점 보고**: push까지 했는지, 병합·배포는 하지 않았다는 것을 적는다.
