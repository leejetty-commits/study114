## 재송동 박스 (11-17 운영 캡처) 원인

캡처: 우동공과 민락점(id 6, 의정부 민락동), 알약 호반베르디움1차(대표)·센텀자이·건영아파트. 「우리동네 민락동 · 호반베르디움1차」 아래 지도 박스가 「재송동」(공부방 2, 학생 0).

- 박스 동 = 지금 고른 알약 슬롯의 `promo_label`(시도 시군구 동 · 단지)에서 뽑은 동(`search-map.js readStudyRoomProviderHomeBanner` ← `resolveStudyRoomMapQuery`). `promo_label`의 동은 `study_room_regions.region_id`의 `regions.dong_name`이다(`StudyRoomHubRepository::promoLabel`).
- 운영(main, #228 전) 알약 CSS는 대표(`is-primary`)와 고른 것(`is-active`)을 **같은 파란 테두리**로 그린다. 캡처에서 호반베르디움1차와 센텀자이 둘 다 파란 것은 **센텀자이가 고른 알약**이라는 뜻이다. 지도도 부산 센텀 일대다.
- 그래서 박스·지도는 이미 고른 알약(센텀자이)을 따라갔고, 「우리동네」 줄만 대표를 계속 보여 줬다(main의 `resolveActiveRegionLabel`이 `peekStudyRoomPromo1()` 고정). #230이 이 줄을 `studyRoomHomePromoLabel(state)`로 바꿔서, 묶음 적용 뒤에는 줄·박스·지도·카드가 같은 알약을 따른다.
- 「재송동」 자체는 **테스트 데이터**다. 센텀자이는 개발 시드 단지(complexes id 3, 부산 해운대구 센텀동로 99)이고 그 동이 regions id 3(옛 가짜 「센텀동」을 재송동으로 바꾼 것)이다. 의정부 공부방에 부산 단지가 홍보지역으로 붙어 있는 상태. 코드 문제 아님. 민락점 등 테스트 데이터는 나중에 일괄 삭제하기로 한 결정(237 결정 문서)대로 두고, 점검은 실제 지역 계정으로 한다.

종현 확인용 SQL (읽기만, phpMyAdmin):
```sql
SELECT sr.id AS room_id, sr.study_room_name, srr.slot, srr.is_primary, srr.region_basis_type,
       srr.region_id, r.sido_name, r.sigungu_name, r.dong_name,
       srr.complex_id, c.name AS complex_name, c.address AS complex_address, c.region_id AS complex_region_id
FROM study_room_regions srr
JOIN study_rooms sr ON sr.id = srr.study_room_id
LEFT JOIN regions r ON r.id = srr.region_id
LEFT JOIN complexes c ON c.id = srr.complex_id
WHERE srr.study_room_id = 6
ORDER BY srr.is_primary DESC, srr.slot ASC, srr.id ASC;
```
예상: 센텀자이 행이 `region_id = 3`, `dong_name = 재송동`, `complex_id = 3`, 주소 부산. 다르면 이 절을 다시 본다.
